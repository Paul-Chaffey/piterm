What it is

A terminal, built rather than approximated

Every previous attempt to put a VT on a BBC micro rendered through the machine's own VDU driver — and inherited its semantics. That driver has no deferred wrap, no second screen buffer, no insert or delete line, and it scrolls the screen if you write the bottom-right cell. Terminals built on it spend their lives compensating.

PiTerm takes the bytes and produces the pixels. It decodes UTF-8, runs a full VT parser, keeps its own cell model with attributes and damage tracking, and blits directly into the Raspberry Pi co-processor's framebuffer. VT semantics are correct by construction, not emulated on top of something that disagrees.

The screen has been checked cell for cell against pyte on captured streams from a real pty — every character and every attribute — and on hardware, rows 1–63 of a live top session matched the reference exactly. All 5,040 cells.

Transport

An SSH client, written for a machine that had none

The terminal used to speak plaintext telnet to a gateway, because the received wisdom was sound: modern key exchange on a 2 MHz 6502 is not viable. That was true, and it was about the wrong processor. The terminal does not run on the 6502 — it runs on the co-processor, where X25519 costs under a millisecond.

Negotiated with OpenSSH 10.2, on the hardware
Key exchangecurve25519-sha256, with kex-strict-c-v00 — the Terrapin mitigation, which matters because the chosen cipher is the one Terrapin targets
Host keyssh-ed25519, signature verified on the co-processor
Cipherchacha20-poly1305@openssh.com, both directions
Authenticationpublic key, Ed25519. Passwords are not implemented and will not be
Compressionzlib@openssh.com, server→client only — so the client needs inflate and never deflate

It is 48,844 bytes of ARM, loaded onto the co-processor and called from BASIC. The crypto core does no I/O at all: bytes in, bytes out, with BASIC keeping the socket. That split is why the terminal above it did not change — and why the same source compiles natively and can be driven against a real sshd on a Linux box, which is where every protocol bug was found rather than on a Beeb through a Tube.

The session key is seeded from the SoC's hardware random number generator, reachable from user mode on this core. RND never goes near it: a predictable ephemeral key does not fail loudly, it produces a working session that a listener can decrypt.

Using it

The ceiling, and getting past it

The Sprow module hands over about 56 bytes per read and a read costs 1.31 cs, so 4,872 bytes a second is the hard ceiling and PiTerm runs at 4,268 of it. Shells, less, vim — anything that redraws when you ask it to — are comfortable inside that.

A monitor that redraws on a timer is not. htop paints roughly 5 KB a frame; at its default 1.5-second refresh that is 3,400 bytes a second against a 4,268 ceiling, and any hiccup grows a backlog that never drains. Measured on a real session, 34.9% of htop's output was colour escapes alone.

Measured at 80×64, 12-second captures
btop as shipped12,812 B/s — 3× over the ceiling, and 2,015 braille characters this font cannot draw
btop -t -u 100003,551 B/s — tty mode: ANSI graph symbols, 16 colours, no braille
htop default3,193 B/s — at 80% utilisation, no headroom
htop -d 50 -Cabout 5× under the ceiling — the one to use

btop is built for a modern terminal — braille graphs, truecolour gradients, block-element meters. -t removes the braille and drops truecolour from 55.5% of the stream to nothing, 3.6× fewer bytes, but a frame is still 21 KB: five seconds of Tube time for a ten-second update. htop is the better tool here.

The terminal cannot simply discard a backlog: VT state is cumulative, so every stale byte still has to be parsed or the screen would be wrong rather than merely late. Parsing costs 1.2% of a session and painting 3.1% — it is the reading that cannot be hurried.

And then the ceiling stopped being the limit

Everything above is measured, and all of it assumed the bytes arrive as the far end wrote them. Inside SSH they do not have to. zlib@openssh.com compresses the stream before it reaches the wire, and a terminal stream is extraordinarily compressible: a third of it is colour escapes, repeated byte for byte on every frame, and deflate's 32 KB window spans several frames of an 80×64 screen.

Same machine, same workload — ten full screen redraws — compression the only difference
Bytes on the wire41,780 → 3,140 — 13.3× fewer
Seconds19.59 → 1.62 — 12.1× faster
Reaching the screen2,092 → 25,295 bytes/sec

The figure that mattered was written down long before it was reachable: a full-screen app at 80×64 needs about 25 KB/sec to feel live, and the module provides 4.3. It now delivers 25,295 bytes a second through the same module, because the ceiling was a property of the encoding and not of the hardware.

The module is no longer the constraint. During the run it was saturated in bursts — 4,008 bytes a second in one five-second window, 1,032 in the next — so what remains is a duty cycle with gaps to fill, not a wall to lift.

Status

Where it stands Running

The display engine, the terminal client and the SSH transport are all finished and verified on the machine. A real shell renders correctly, byte-lossless, at 80×64, and holds for as long as it is left running — the longest sessions so far are a few minutes because that is how long the tests ran, not because anything ends them.

The SSH client was written from nothing in a day, from an assessment to a working terminal. There was no prior art — no SSH client has existed for a BBC Micro before, and the RISC OS ones do not port: one is SSHv1 and unmaintained, the other needs GTK.

Still open

  • Host keysThe client verifies the host key signature, which proves the server holds the key it presented. It does not yet judge whether that is the key you meant — there is no known_hosts on the Beeb, so the fingerprint is compared by eye.
  • GlyphsBraille, shading blocks and arrows are unmapped, so a program drawing graphs with them draws nothing. The font is harvested from the Pi VDU driver and simply has no such characters; braille is tractable, since a cell is 2×4 dots and the codepoint's low byte is the pattern.
  • The idle gapWith compression the module is no longer the constraint — it was saturated in bursts and idle between them. That is a duty cycle rather than a rate limit, and nobody has yet looked at what fills the gaps.
  • Post-quantumThe key exchange is classical, and OpenSSH 10.1 warns clients when it is. Servers still accept curve25519-sha256 and no removal is scheduled, but mlkem768x25519 is what this would eventually want.

Settled earlier: the defect that blocked all of this for weeks

Kept because it is the most useful thing this project learned. For weeks the co-processor wedged after tens of thousands of Tube transactions, and the terminal was blamed. It was never the terminal, and it was never one fault.

The host's screen mode. A dead CMOS battery had pinned the machine in MODE 0, so every measurement ever taken was made in it. In MODE 7 the same test passes where MODE 0 froze four times out of four.

A missing capacitor. The interface board carries no bulk decoupling at all, while mounting a Pi 3A+ held at 1.2 GHz. The 5 V rail sagged under the Pi's transients and the Tube silently dropped one byte per 874,000 — uniformly distributed, always exactly one byte, invisible to any test that does not checksum the transfer. One load in ten of the terminal's own program arrived with a byte missing, so it ran for minutes and then walked into the damage.

1000 µF and 100 nF across 5 V and ground took that to zero errors in 13.1 MB. The terminal needed no change at all; the correct program had been arriving corrupted.

Every figure on this page was measured on the physical machine, not estimated and not scaled from an emulator — a rule adopted after an emulator-derived prediction came in wrong by a factor of fifty. The compression figures were predicted on a Linux box first and then measured on the Beeb; the two agreed to 0.24%.
